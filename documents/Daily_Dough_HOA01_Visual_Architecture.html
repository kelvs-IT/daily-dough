Project Overview & Executive Summary

Daily Dough is an on-demand mobile commerce platform specializing in artisanal handcrafted donuts and specialty espresso drinks. The platform employs a modern Three-Tier M-Commerce Architecture designed to provide seamless customer purchasing on Android mobile devices alongside complete managerial visibility and control for store administrators via a responsive web dashboard.

📘 Academic Architecture Note: Cloud Firestore vs. Realtime Database

While the baseline ITE 7 Module introduces Cloud Firestore, the Daily Dough platform implements Firebase Realtime Database (RTDB) via persistent REST/HTTP communication. This architectural choice delivers ultra-low-latency order lifecycle synchronization (Pending → Processing → Delivered) and enables the Single Page Web Dashboard to run efficiently with zero external library overhead.

Provides a high-level view of the entire Daily Dough system. It illustrates the role separation between mobile customer shopping and web-based store management, connected through shared cloud services.

Key Components

  • Customer Mobile App: Native Android client built with Flutter.
  • Web Admin Dashboard: Desktop management SPA for store admins.

Purpose & Overview

Illustrates the internal software architecture of the mobile shopping application, following clean Model-View-Service separation.

Key Components

  • Screens (`lib/screens/`): 7 user-facing views handling the complete customer purchase lifecycle.
  • `FirebaseService`: Central ChangeNotifier state manager with in-memory caching.
  • Domain Models: Strongly-typed Dart classes for items, carts, and orders.
  • Plugins: Platform channels linking native Android code to Dart.

Data Flow

User gestures on screens invoke methods on `FirebaseService`. The service updates local cache, synchronizes with Firebase via HTTP REST, and triggers reactive UI updates.

End-to-End Order Lifecycle 
sequenceDiagram
    autonumber
    actor Customer as Customer (Mobile App)
    participant Mobile as Flutter App (FirebaseService)
    participant Cloud as Firebase Realtime Database
    participant AdminApp as Web Admin (app.js)
    actor Admin as Store Administrator

    Note over Customer,Admin: Step 1: Customer Browsing & Ordering
    Customer->>Mobile: Opens Mobile App, browses donuts and coffees
    Mobile->>Cloud: GET /products.json
    Cloud-->>Mobile: Returns live product menu array
    Customer->>Mobile: Adds Pistachio & Hot Cafe Latte to Cart
    Customer->>Mobile: Enters Delivery Address, selects Payment (GCash)
    Customer->>Mobile: Taps "Confirm Order"
    Mobile->>Cloud: POST /orders.json & POST /transactions.json (stage: "Pending")
    Cloud-->>Mobile: HTTP 200 OK (Order ID Created)
    Mobile->>Customer: Order placed! Navigates to Live Order Tracking Screen

    Note over Cloud,Admin: Step 2: Administrator Real-Time Notification & Processing
    AdminApp->>Cloud: Periodic Polling (GET /transactions.json)
    Cloud-->>AdminApp: Returns updated transactions list with new Pending order
    AdminApp->>AdminApp: Increments Notification Bell Badge (🔔 1) & Updates KPI Cards
    Admin->>AdminApp: Clicks Notification Bell & views order details
    Admin->>AdminApp: Changes Order Status from "Pending" to "Processing"
    AdminApp->>Cloud: PATCH /transactions/{id}.json {"stage": "Processing"}
    Cloud-->>AdminApp: HTTP 200 OK (Updated in Cloud)

    Note over Customer,Mobile: Step 3: Customer Live Status Synchronization
    Mobile->>Cloud: Polls / Streams Customer Orders (GET /transactions.json)
    Cloud-->>Mobile: Returns Order with updated stage ("Processing")
    Mobile->>Customer: Tracking Screen updates: Stage 2 "Baking & Preparing" Active!

    Note over Cloud,Admin: Step 4: Order Delivery Completion
    Admin->>AdminApp: Updates Order Status to "Delivered"
    AdminApp->>Cloud: PATCH /transactions/{id}.json {"stage": "Delivered"}
    Cloud-->>AdminApp: HTTP 200 OK
    Mobile->>Cloud: GET /transactions.json
    Cloud-->>Mobile: Returns Order with stage "Delivered"
    Mobile->>Customer: Tracking Screen shows "Order Delivered! Enjoy your treats."

Purpose & Overview

Demonstrates the end-to-end communication sequence of an order from customer submission to final delivery.

Key Steps

  • 1. Placing Order: Mobile app writes order details to `/orders` and `/transactions`.
  • 2. Admin Notification: Dashboard detects new order, triggers bell badge and audio alert.
  • 3. Kitchen Processing: Admin updates status to *Processing*, advancing customer tracking UI.
  • 4. Completion: Admin marks order as *Delivered*, completing the transaction.

Data Flow

All state transitions occur asynchronously via cloud REST endpoints. No direct mobile-to-web connection is needed.
